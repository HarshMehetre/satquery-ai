# SatQuery-AI Developer Handoff

Last reviewed: 2026-09-07

## 1. Project Purpose

SatQuery-AI is intended to turn a natural-language geospatial question into a validated execution plan, run deterministic satellite and GIS operations, and return spatial results with provenance/evidence.

The guiding architecture is:

```text
Natural-language intent
        -> QueryPlan
        -> dependency resolution
        -> validated operations
        -> ExecutionResult
```

The repository currently contains the execution core and operation implementations. The natural-language planner, HTTP API, and application entry point are not implemented yet.

## 3. Runtime Architecture

### Query and plan schemas

`QueryPlan` is the top-level execution contract. It contains:

- `plan_id`: unique plan identifier.
- `aoi`: area of interest with type `bbox`, `polygon`, or `place` and flexible value.
- `inputs`: declarative external data sources represented by `DataInput`.
- `operations`: ordered or dependency-linked `Operation` objects.
- `output`: requested output format and inclusion flags.

An `Operation` has an `id`, registered `type`, input IDs, and arbitrary operation-specific `parameters`.

### Dependency resolution

`DependencyResolver.resolve()`:

1. Rejects duplicate operation IDs.
2. Treats an input ID matching an operation ID as an operation dependency.
3. Treats all other input IDs as external inputs at this stage.
4. Performs a depth-first topological sort.
5. Raises `ValueError` for circular dependencies.

Missing runtime/declarative inputs are checked later by `Executor._validate_inputs()`.

### Execution

`Executor.execute(plan, runtime_inputs=None)` creates an `ExecutionContext`, resolves operation order, and for each operation:

1. Validates that referenced IDs exist in plan inputs, runtime inputs, or previous results.
2. Looks up the implementation in `OperationRegistry`.
3. Calls `validate()`.
4. Calls `execute()`.
5. Stores the returned `OperationResult` in `context.results`.

The final return value is an `ExecutionResult` containing operation results, evidence, and metadata.

### ExecutionContext state

`ExecutionContext` owns the mutable state for one execution:

- `aoi`: plan area of interest.
- `inputs`: declarative `DataInput` objects keyed by ID.
- `runtime_inputs`: actual in-memory external data keyed by ID.
- `results`: `OperationResult` objects produced during this execution.
- `evidence`: accumulated provenance records.
- `metadata`: execution-level metadata.

Use `add_result()` and `get_result()` for operation results. `get_runtime_input()` returns raw runtime data. `get_input_result()` resolves operation results and, when supplied, runtime `OperationResult` wrappers.

### Important input contract

The current codebase has two runtime-input conventions:

- Some operations, especially NDVI and the current `ProjectToCRSOperation`, consume raw runtime data such as `RasterData` or `GeoDataFrame`.
- Other operations use `get_input_result()` and therefore expect runtime inputs to be wrapped in `OperationResult`.
- Operations generated by the plan itself always produce `OperationResult` values in `context.results`.

This inconsistency is a known design issue. New code should choose one convention and apply it across all operations. Until then, inspect the operation implementation and its tests before constructing `runtime_inputs`.

## 4. Operation Registry and Implementations

`OperationRegistry` maps plan operation names to `BaseOperation` subclasses. It rejects duplicate registrations and raises `KeyError` for unknown operation types.

The test registry in `tests/operations/registry.py` is separate from any future production registry. It uses deterministic mocks for external satellite and OSM retrieval while reusing most real processing operations.

Current operation families:

| Type | Operation | Main input/output |
| --- | --- | --- |
| Satellite | `get_satellite_imagery` | Sentinel-2 request -> raster `OperationResult` |
| Remote sensing | `calculate_ndvi` | red/NIR raster -> one-band NDVI raster |
| Remote sensing | `temporal_difference` | two rasters -> raster difference |
| Remote sensing | `vegetation_loss` | change raster + threshold -> loss mask raster |
| Remote sensing | `raster_polygonize` | one-band raster mask -> GeoDataFrame |
| GIS | `get_osm_features` | bbox + feature type -> GeoDataFrame |
| GIS | `project_to_crs` | vector GeoDataFrame -> projected GeoDataFrame |
| GIS | `buffer` | projected vector -> buffered vector |
| GIS | `intersection` | two matching-CRS vectors -> vector intersection |
| GIS | `area` | projected vector -> scalar area result |

All operations implement `BaseOperation.validate()` and `BaseOperation.execute()` and return an `OperationResult`.

## 5. Data and State Models

### Raster data

`RasterData` stores:

- `data`: NumPy array, normally shaped `(bands, height, width)`.
- `bands`: ordered band names such as `B4`, `B8`, or `NDVI`.
- `metadata`: `RasterMetadata` containing CRS, transform, dimensions, resolution, bounds, nodata, count, and dtype.

`RasterData` allows arbitrary NumPy types through Pydantic configuration.

### Vector data

Vector operation results use a GeoPandas `GeoDataFrame` in `OperationResult.data`. CRS is expected to be present when projecting, intersecting, buffering, or calculating area.

### Results

`OperationResult.data_type` is one of `raster`, `vector`, `table`, `scalar`, or `json`. The `data` field is intentionally flexible. Operation-specific metadata belongs in `OperationResult.metadata`; execution-wide metadata belongs in `ExecutionResult.metadata`.

### Evidence

`Evidence` models source, source type, optional acquisition date, operation, parameters, and description. Evidence accumulation is supported by `ExecutionContext`, but `app/evidence/builder.py` is currently empty and the executor does not automatically build evidence.

## 6. External Dependencies

Declared in `requirements.txt`:

- `pydantic>=2.0`: schema validation.
- `pydantic-settings>=2.0`: environment-backed settings.
- `numpy>=1.24`: raster calculations.
- `sentinelhub`: Sentinel-2 data access.
- `geopandas`: vector data and CRS operations.
- `osmnx`: OpenStreetMap feature retrieval.
- `shapely`: geometry primitives and operations.
- `pytest`: test runner.

Rasterio is used directly by the code/tests for transforms and polygonization and is installed transitively through the geospatial stack. It should be treated as an operational dependency even though it is not listed explicitly in `requirements.txt`.

Configuration is loaded from `.env` through `app/config/settings.py`:

- `SENTINEL_CLIENT_ID`
- `SENTINEL_CLIENT_SECRET`

The Sentinel retrieval operation raises a clear error when credentials are absent. Tests should use mocks and should not require live Sentinel or OSM services.

## 7. Developer Commands

From the repository root on Windows:

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

Run a focused test:

```powershell
.\.venv\Scripts\python.exe -m pytest tests/executor/test_hero_pipeline.py -v
```

The repository configures `pytest` with `pythonpath = ["."]` and discovers tests under `tests/`. Ruff is configured with an 88-character line length, but no lint script is currently defined.

Use the repository virtual environment. The global `python`/`pytest` commands may point to an interpreter without the project dependencies.

## 8. Testing Rules

- Prefer deterministic fixtures and mocks for satellite and OSM calls.
- Test operation validation failures as well as successful calculations.
- Preserve CRS, raster dimensions, band names, transforms, and metadata in result assertions.
- Use realistic `OperationResult` wrappers when testing operations that consume prior operation results.
- Keep external-network tests out of the default suite.
- For pipeline tests, make the plan's operation graph agree with the supplied runtime inputs. Do not define an operation that produces an ID and simultaneously pretend that ID is only an external fixture unless that behavior is intentional and tested.
- Test projected geometries before calculating metric area. Geographic CRS area is rejected by design.

## 9. Current Known Gaps and Risks

1. **Application wiring is incomplete.** `app/main.py` and `app/api/routes.py` are empty.
2. **Planner validation is incomplete.** `app/planner/validator.py` is empty; `QueryPlan` validation is currently mostly Pydantic field validation.
3. **Evidence generation is incomplete.** `app/evidence/builder.py` is empty and execution does not automatically populate evidence.
4. **Runtime input contracts are inconsistent.** Normalize this before adding more pipeline operations.
5. **Production registry construction is not centralized.** Tests construct their own registry; the application needs a production registry/factory.
6. **Sentinel and OSM integrations are live-service boundaries.** Keep them behind adapters or mocks for reliable tests.
7. **Dependency declaration is incomplete for direct imports.** Review and pin the geospatial stack, especially rasterio, for reproducible environments.
8. **The current worktree has user changes in test support files.** Review `tests/executor/test_hero_pipeline.py`, `tests/operations/mocks.py`, and `tests/operations/registry.py` before modifying them; do not assume the previous test fixture state.

## 10. Recommended Next Decisions

1. Standardize runtime inputs as either raw domain data or `OperationResult` wrappers. The cleaner long-term choice is one resolver in `ExecutionContext` that returns a consistent `OperationResult` view.
2. Add a production registry factory containing the real operation classes.
3. Implement planner validation for operation IDs, input references, parameters, and output compatibility.
4. Implement evidence creation at operation boundaries or in the executor.
5. Add API/application wiring only after the execution contract is stable.
6. Make direct geospatial dependencies explicit and pin a known-compatible environment.

## 11. Change Discipline

- Keep planner logic separate from deterministic execution.
- Keep operations small and domain-focused; do not put orchestration inside an operation.
- Preserve public schema fields unless a migration is intentional.
- Validate inputs before expensive remote or geospatial work.
- Avoid live network calls in unit tests.
- Do not rewrite unrelated user changes in a dirty worktree.
- Run the narrowest relevant test after a change, then the full suite when shared contracts change.
